Fabric 平台授权卡片个性化（一期 MVP）

让授权卡片能识别调用方身份并显示对应文案
📅 创建：2026-05-18 🏷️ 版本：v1.1 👤 作者：张振
1背景与问题

当前 Fabric 平台的授权卡片只能显示统一文案（如 "请求访问以下权限"），无法区分不同调用方。 随着 POPO-CLI、POPO Bot、未来更多业务方接入 Fabric，需要支持按调用方身份显示个性化授权文案。

⚠️ 旧方案被否原因
旧方案把"业务方文案"挂在租户的应用配置下，存在两个问题：
  • 业务方调用时没有身份，Fabric 不知道谁来调用，无法选对应文案
  • 授权支持跨租户多应用批量授权，文案不能绑定在某个 App 上

本方案站在 Fabric 平台视角，将业务方（Caller）作为系统级独立实体，文案跟随 Caller 维护。

📌 v1.1 变更说明
新增覆盖场景：POPO-CLI 首次安装时调用 Fabric 应用授权接口，也统一走 Caller 机制（带 caller_id 参数）。Fabric 端不再为 POPO-CLI 硬编码识别身份。详见第 4 章。
2一期范围（做 vs 不做）

✅ 一期要做（仅 3 件）

  • 引入「业务方（Caller）」作为系统级实体，存表
  • API 调用支持通过 Header X-Caller-ID 声明身份
  • 授权卡片渲染时按 Caller 身份显示对应文案

❌ 一期不做（明确放二期）

  • 不做业务方管理后台（一期用 SQL 直接插）
  • 不做密钥签名校验（一期信任 Header）
  • 不做调用权限白名单（一期任何 Caller 可调任何 App）
  • 不做业务方 Logo 展示
  • 不做业务方状态管控（disable/enable）
  • 不做调用审计与统计
💡 一期设计原则
"一期做的事，二期不需要推翻。" 一期只立"骨架"，二期是给骨架"穿衣服"。
3数据模型

新增表 caller，仅 4 个字段：

字段类型必填说明
caller_idVARCHAR(64)是（主键）业务方唯一标识，如 popo-cli
caller_nameVARCHAR(128)是业务方展示名，如 POPO CLI
card_copyVARCHAR(255)是授权卡片文案，如 POPO CLI 请求访问以下权限：
created_atTIMESTAMP是创建时间

一期数据由 DBA 手动 SQL 插入：

-- POPO-CLI 接入
INSERT INTO caller (caller_id, caller_name, card_copy) VALUES
  ('popo-cli', 'POPO CLI', 'POPO CLI 请求访问以下权限：'),
  ('popo-bot', 'POPO Bot', 'POPO Bot 请求访问以下权限：');
4一期覆盖的两个调用场景（统一走 Caller 机制）

一期 Caller 机制同时覆盖两个 POPO-CLI 调用 Fabric 的场景，共用同一张 caller 表、同一份 card_copy 文案、同一套识别逻辑。Fabric 端不再为 POPO-CLI 做硬编码特例。

场景触发时机调用 Fabric 的方式当前现状
① 首次安装授权 用户执行 install-v1.sh 后，POPO-CLI 调用 Fabric 应用授权接口 调用授权接口时带入 caller_id=popo-cli 当前 Fabric 端硬编码识别为 POPO-CLI，需改造
② 日常 API 调用 Agent 通过 popo-cli 调用 Fabric API 时 请求 Header 携带 X-Caller-ID: popo-cli 当前 Fabric 端无业务方识别能力，需新增
💡 这样设计的好处
  • 不为 POPO-CLI 开特殊通道——POPO-CLI 在 Fabric 眼里只是一个普通业务方，跟未来 POPO Bot、其他业务方接入路径完全一致
  • 统一性——首次授权与日常调用走同一套 caller 识别逻辑，没有"安装时特例代码"
  • 未来业务方接入零特例——新业务方接入时仅需注册一条 caller 数据 + 调用时带 caller_id，Fabric 端永远不需要为新业务方加硬编码
5接口协议

场景 ① 首次安装授权

POPO-CLI 调用 Fabric 应用授权接口时，带入 caller_id 参数：

# 示例（具体接口路径以 Fabric 现有授权接口为准）
POST /api/v1/open-apis/gateway/auth/install
Body:
  {
    "caller_id": "popo-cli",
    "device_info": {...}
  }

场景 ② 日常 API 调用

业务方调用 Fabric API 时，请求头携带 X-Caller-ID：

POST /api/v1/open-apis/gateway/appcode/popo/_invoke
Headers:
  X-Caller-ID: popo-cli
Body:
  {"tool": "popo_message_send_p2p", "params": {...}}

Fabric 平台接收逻辑（伪代码）

def get_card_copy(request):
    # 兼容两种入参方式
    caller_id = request.headers.get("X-Caller-ID") or request.body.get("caller_id")

    if not caller_id:
        return DEFAULT_COPY  # "请求访问以下权限："

    caller = db.query("SELECT card_copy FROM caller WHERE caller_id = ?", caller_id)

    if caller:
        return caller.card_copy
    else:
        return DEFAULT_COPY  # 未注册的 caller 走默认文案
✅ 兜底策略
Header 未传或 caller_id 未注册时，统一使用默认文案，不影响业务调用。

8一期 → 二期演进路线图

一期是骨架，二期是给骨架穿衣服。所有二期能力都是"加字段、加 UI、加校验"，不需要推翻一期的数据模型与接口协议。

一期 MVP

建立 Caller 实体

  • 4 字段 caller 表
  • Header X-Caller-ID 自报
  • 授权卡片文案按 Caller 渲染
  • SQL 手动管理数据
→
二期完整版

给 Caller 穿衣服

  • caller 表加 secret / logo / status / allowed_apps 字段
  • 新增 X-Caller-Sign 做签名校验
  • 新增 "Caller 管理" 后台菜单（CRUD）
  • 授权卡片加 Logo + 来源信息
  • 调用审计 + Caller 维度报表

演进影响分析（一期到二期不会改 / 删什么）

关键决策 一期实现 二期演进 是否推翻一期？
Caller 表结构 4 个字段 加 secret、logo、status、allowed_apps 字段 ❌ 只加字段
业务方身份识别 读 X-Caller-ID 增加 X-Caller-Sign 签名校验 ❌ 兼容增强
文案归属 挂在 caller 上 不变 ❌ 不变
配置入口 SQL 手动 加管理后台 UI ❌ 只加 UI
跨租户多应用授权 天然支持 不变 ❌ 不变
未注册 Caller 走默认文案 可选拒绝调用（需手动 enable） ⚠️ 行为变化（需提前通知接入方）
✅ 演进安全性结论
6 项关键决策中，5 项是纯增量演进（加字段、加 UI、加校验），不需要改一期代码或数据； 仅 1 项（未注册 Caller 的处理策略）在二期可能调整行为，但完全可以通过配置开关平滑切换。
9附录：术语表
术语说明
Caller（业务方 / 调用方）调用 Fabric API 的上游系统，如 POPO-CLI、POPO Bot
App（应用）Fabric 平台内注册的功能模块，如 POPO、KM 等，每个 App 含多个 API
Tenant（租户）Fabric 上的组织单位，一个 Caller 可跨多个租户的多个 App 调用
授权卡片用户首次或重新授权时收到的 POPO 卡片消息，确认是否授权某个 Caller 调用
