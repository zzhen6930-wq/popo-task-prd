WrokHub Studio · AI 能力「会话管理」升级

把会话从"只留首尾"升级为"全链路可观测"：结构化事件流 + Token / 耗时 / 时间，让每一次对话都能被排查、被度量。
📅 2026-07-23 🏷️ v1.0 👤 作者：青远（张振） 🧩 归属：WrokHub Studio / AI 能力 · 会话
1背景与目标

WrokHub Studio 后台已有「会话」模块，可按 智能体 / 用户 / 时间查询会话列表与详情。但当前实现只记录了用户输入与 Agent 最终输出，中间的模型思考、工具调用、知识检索、报错等过程信息全部缺失，导致：

  • 无法排查问题：Agent 回答不对 / 变慢 / 报错时，看不到中间发生了什么，只能靠猜
  • 无法度量成本与性能：单次会话消耗多少 Token、每一步耗时多久，都无从统计
  • 无法定位瓶颈：哪一步工具慢、哪次检索没命中、哪里报错重试，没有抓手
  • 渠道来源不清：无法区分会话来自 POPO-私聊、POPO-群聊、Workhub 还是 SDK，难做分渠道分析

本期目标：升级会话管理的数据采集与可视化——将模型思考、调用工具、Skills、MCP、知识检索、模型输出、系统信息、报错信息等过程事件结构化记录并回放，并在每个事件上标注消耗 Token、耗时、开始时间；列表页补齐应用场景、来源与消耗 Token。参考同类 Agent 观测台（Trace / Timeline）的事件流交互形态（见参考图 1/2/3）。

🔑 一句话定位
给会话装上「行车记录仪 + 仪表盘」：完整回放对话每一步的过程，并量化每一步的 Token 与耗时，让排查从"靠猜"变成"看轨迹"。
2核心概念与术语
术语说明
会话（Session / Conversation）持久聊天线程：一个用户（或一个群）与某个智能体的完整对话，拥有唯一 conversation_id；由若干轮消息构成，用户可随时回到同一会话继续对话。列表页一行 = 一条会话线程（非一次运行）
运行（Run / 一轮）会话内 Agent 处理一轮请求的执行实例：用户发起 → 思考 / 调用工具 / 检索 → 产出结果。run 不作为列表主粒度，在详情页事件流中作为线程内的分段呈现
会话状态（Status）线程维度状态，本期枚举：进行中（当前有一轮 run 正在执行）/ 空闲（等待用户下一句，线程存活可续聊）/ 已关闭（用户主动结束或超时归档，不可再续）/ 异常（最近一轮 run 失败，需排查）
事件（Event）会话内一次可被记录的最小过程单元，拥有唯一 event_id（如 sevt_…），带类型、开始时间、耗时、Token 等元数据
事件类型（Event Type）见第 4 节：用户输入 / 模型思考 / 调用工具 / Skills / MCP / 知识检索 / 模型输出 / 系统信息 / 报错信息
应用场景（Channel）会话的产生来源，本期枚举：POPO-私聊POPO-群聊WorkhubSDK
来源（Source）会话产生的上游系统，本期枚举：Agenthub / Workhub Studio / Claude Code / OpenClaw / CodeX / Hermes
消耗 Token事件级：该事件的 输入 Token / 输出 Token（如 5.6k / 69）；会话级：全部事件累计的总 Token
耗时（Duration）单个事件从开始到结束的时长（毫秒 / 秒）；会话级为总时长
开始时间（Offset）事件相对会话起点的偏移时间（如 0:00:11），用于还原时间线顺序
会话空闲（Idle）相邻事件之间用户无操作的间隔，事件流中以分隔条标注（如"会话空闲 · 31.6 秒"）

4事件模型（9 类事件）

会话详情把整段对话拆解为一串结构化事件，每个事件都带统一的元数据（event_id、类型、开始时间、耗时、消耗 Token），并按需携带各自的业务字段。事件类型如下：

事件类型角色标签结构化记录内容展示指标
用户输入 用户用户 query 文本、附件（文件/图片）、可选 tenantId 等入参开始时间
模型思考思考模型的思考 / 推理过程文本（thinking / reasoning）Token（总消耗）、耗时、开始时间
调用工具工具工具名、输入参数（tool_use）+ 返回结果（tool_result，含来源链接）Token、耗时、开始时间
SkillsSkills技能名、命中的技能指令、输入 / 输出Token、耗时、开始时间
MCPMCPMCP Server、method、请求参数、返回结果Token、耗时、开始时间
知识检索知识检索 query、命中片段、相关性分数、知识库 / 来源Token、耗时、开始时间
模型输出AgentAgent 最终回复（支持 Markdown 渲染，如表格 / 列表 / 链接）Token、耗时、开始时间
系统信息系统系统级事件：会话空闲、上下文压缩 / flush、状态变更、限流等耗时、开始时间
报错信息报错错误码、错误消息、发生阶段、堆栈 / 原始返回，可标记重试耗时、开始时间
采集完整性
"调用工具"需成对记录 tool_use（输入）与 tool_result（输出）并归属同一事件组；报错信息必须独立成事件、不得被吞没在正常输出里，以便排查。

6会话详情页改造（事件流）

详情页由"两条消息"改造为按 run 分组的结构化事件流时间线。整体分为：①顶部标识 + 检索区 → ②按 run 分组的事件流列表（分页） → ③右侧详情抽屉。

6.1 顶部区（会话标识 + 检索区）

会话是持久聊天线程，详情页会累积几十上百轮对话，因此顶部由原先的"归因展示区"调整为「极简标识 + 检索区」：归属类信息（应用场景 / 知识库 / 会话 ID）列表页已可见，不在详情页重复占位；总耗时因跨天累加无解释力，下沉到每一轮 run。

元素变化说明
智能体名称 + 状态保留标题行，状态见 5.1 线程状态枚举
总消耗 Token保留该会话累计总量（输入 / 输出）
上次对话时间保留相对时间，如「15 小时前」
总耗时去掉持久线程累计耗时无意义，改为每轮 run 各自的耗时
应用场景 / 知识库 / 会话 ID去掉列表页已可见，详情页不再重复展示

新增检索区（位于标题行下方），用于在长线程中定位对话，各条件可叠加：

筛选项形态说明
用户邮箱输入框按发言人过滤；判定为「run 内任一参与人匹配即保留整通 run」。群聊场景一轮 run 可能多人发言，可用于定位某人参与过的对话；私聊场景唯一
关键字输入框过滤条件（非高亮跳转）：命中即保留整通 run，未命中的 run 整体过滤掉，保证上下文完整
时间范围区间选择器单个筛选项，展开后在同一浮层内选择开始时间与结束时间，支持只填一端（另一端不限）；按 run 开始时间过滤
事件类型多选下拉原 All events 筛选，位置移入检索区；命中该类事件的 run 才展示

6.2 事件流列表（按 run 分组）

会话为持久线程，内部由多通 run（一轮对话）构成。事件流按 run 分块展示，避免长列表平铺看不出轮次边界。

  • run 块头展示该轮汇总：开始时间 · 本轮耗时 · 本轮消耗 Token（总消耗）· 本轮结果（成功 / 失败）。不展示「第 N 轮」与单个用户邮箱——群场景一轮 run 可能由多人发言合并触发，单一邮箱无法准确表达。
  • run 内事件按时间线逐行展示：左侧角色标签，中间内容摘要，右侧 Token（总消耗）· 耗时 · 相对时间。
  • 发言人下沉到事件行：「用户」类事件的角色标签展示为 用户：<用户邮箱>，从而在一轮 run 中清晰表达有几个用户参与、分别在什么时间参与（IM 群场景多人输入合并为一个问题时尤其必要）；私聊场景形态一致，仅为单一邮箱。
  • Token 口径：本期不再区分输入 / 输出，统一展示总消耗（= 输入 + 输出）。会话顶部展示整条会话总消耗，run 块头展示本轮总消耗，事件行展示该步骤总消耗。
  • 两通 run 之间以分隔条标注会话空闲时长（如「会话空闲 · 31.6 秒」「会话空闲 · 21 小时 26 分」）。
  • 分页：按 run 粒度分页（run 内事件不拆页），保证单轮上下文完整；页脚展示「共 N 轮对话 · 第 X/Y 页」与上/下一页。分页参数与交互细节由研发按实现选型决定。
  • 筛选联动：6.1 各筛选条件命中判定均以 run 为单位——命中则整通 run 保留，不命中整体过滤；筛选变化后分页重算并回到第 1 页。

6.3 Events 筛选（默认 All events）

事件类型筛选位置移入 6.1 检索区，默认「All events / 所有活动」；可按事件类型多选过滤（如只看「调用工具 + 报错」用于排障，或只看「用户 + 模型输出」还原对话）。判定以 run 为单位：run 内存在选中类型的事件则该 run 保留。可与用户邮箱、关键字、时间条件叠加。筛选只影响展示，不改变原始记录。

6.4 右侧详情抽屉

点击任一事件行，右侧滑出详情抽屉（参考图 2 / 图 3），展示该事件的完整结构化内容：

  • 头部：事件类型 + 事件名（如 网络搜索 / 信息）、event_id、开始时间、耗时
  • 视图切换：渲染（友好排版，如 Markdown 表格）/ 原始（raw payload）/ Deltas（流式增量，模型输出类事件适用）
  • 调用工具类：分区展示 agent.tool_use（输入查询）与 agent.tool_result（返回结果，含来源链接、可跳转），每段可复制
  • 模型输出类：展示渲染后的完整回答；报错类：展示错误码、消息、堆栈；知识检索类：展示命中片段与来源

8数据采集要求（研发对齐）
  • 全过程落库：运行时把 9 类事件按发生顺序写入会话事件表，字段含 event_id / conversation_id / type / role / start_offset / duration / token_in / token_out / payload。
  • 渠道标记：会话创建时写入 channel（POPO-私聊 / POPO-群聊 / Workhub / SDK）与 group_id（仅群聊场景），供列表列与筛选使用。
  • 成对记录：工具 / MCP / Skills 的调用与返回成对入库并可关联为同一事件组。
  • 报错不吞没：任何阶段异常都单独记为 error 事件，保留错误码与原始返回。
  • 原始可回放：payload 同时保留 渲染所需结构 与 raw 原文，支撑抽屉「渲染 / 原始 / Deltas」切换。
  • Token 汇总：会话级总 Token 由事件级累加得出，保证列表与详情口径一致。

10验收标准
  1. 列表页可见并可筛选应用场景、来源，可见消耗 Token 且与详情总量一致。
  2. 详情页能完整回放一次含工具调用 / 知识检索 / 报错的会话，9 类事件均正确归类。
  3. 每个事件行正确显示 Token / 耗时 / 开始时间；空闲分隔条正确。
  4. events 筛选默认 All events，切换后事件流按类型正确过滤。
  5. 点击事件右侧抽屉展示完整详情，且「渲染 / 原始」可切换、内容可复制。
  6. 报错事件独立可见，含错误码与原始返回，可用于排查。
